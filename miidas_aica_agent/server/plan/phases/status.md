## Gate B RC checklist

- `server/plan/architecture.md#gate-b-rc-checklist` が canonical checklist である。
- `status.md` は architecture.md の checklist に対する実行結果とリンクだけを保持し、別個の判定基準を持たない。
- architecture.md の threshold 記録と evidence が埋まるまで RC 判定をしない。
- checklist 更新前に未記入項目があれば RC を見送る。

## ステータス値

- `not-started`
- `ready`
- `in-progress`
- `blocked`
- `review`
- `done`

完了ルール:
- `verification.md` で、すべての必須コマンドが `pass`、`waived`、または `not-applicable` と示されていない限り、`done` は無効。
- `waived` には、オーナー、理由、日付、フォローアップが必要。
- `not-applicable` には理由が必要。
- 必須コマンドに `fail` または `not-run` がある場合、ステータスは `done` ではなく、`blocked`、`in-progress`、または `review` にする必要がある。
- critical scenario の waiver は `server/plan/phases/gate_a_scenario_matrix.md` の Waiver severity に従う。Gate A owner の明示承認なしに critical scenario を `waived` にしてはいけない。
- 機械検証: `PYTHONPATH=server/src/aica_agent .venv-server/bin/python server/plan/lint_status_verification.py` を実行し、`status.md` と `verification.md` の整合を確認する。

## owner 割当プロセス

1. Gate A owner をこの file の概要に追記する。
2. Gate A owner が phase owner を決め、RACI 対応表の `現在の割当` を更新する。
3. phase owner が task owner と branch/PR をステータス表へ記録する。
4. `オーナー` と `ブランチ/PR` が埋まった task だけを `ready` に変更できる。
5. owner 未割当のまま作業を始めた場合、その task は `in-progress` ではなく `blocked` のままとする。

## オーナー割当ルール

- `オーナー` と `ブランチ/PR` が未割当の task は `ready` にしてはいけない。
- waiver 承認者としての Gate A owner は、最初の task を `ready` にする前にこの file の概要へ追記する。
- task owner は、該当 task の `handoff.md` / `verification.md` / `server/plan/phases/status.md` の更新責任を持つ。
- `gate_a_scenario_matrix.md` の evidence owner と status table の task owner が違う場合、`handoff.md` に分担理由を書く。
- `gate_a_scenario_matrix.md` の owner label は下記 RACI 対応表の status task に紐づく。対応 task の `オーナー` と `ブランチ/PR` が未割当の間、その owner label が担当する scenario は `ready` にしてはいけない。

## task doc 粒度ルール

- Phase 1 / Phase 2 の task は shared boundary と初期 scaffold を作るため、`task.md` に許可ファイル、実装メモ、fallback command を具体列挙する。
- Phase 3 以降の task は task 数が多いため、`task.md` は薄く保ち、source of truth を親 feature README、親 phase README、`server/plan/phases/gate_a_scenario_matrix.md` に集約する。
- Phase 3 以降の task owner は、着手時に親 feature README と matrix の該当 scenario / marker membership を読み、必要なら task-local の `実装メモ`、`verification.md`、`handoff.md` を具体化してから `in-progress` にする。
- Phase 3 以降でも critical scenario を担当する task は、`done` にする前に `verification.md` に実行コマンド、fixture path、matrix evidence 更新結果を具体値で記録する。
- 薄い `task.md` は完了判定を弱めるものではない。`verification.md`、`handoff.md`、`gate_a_scenario_matrix.md` が具体値で更新されていない task は `done` にしてはいけない。

## handoff 更新タイミング

- 実装中: 設計判断、互換性メモ、後続 task への注意点が発生した時点で `handoff.md` に追記してよい。
- task 完了前: `handoff.md` の `未実装` / `未記入` / placeholder を実値へ置き換える。
- `done` 変更前: `handoff.md`、`verification.md`、`server/plan/phases/status.md` がすべて更新済みであることを確認する。
